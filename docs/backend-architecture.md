# Backend Architecture

## Structure

```text
apps/api/
├── cmd/server/main.go
├── internal/
│   ├── app/ config/ database/ middleware/ platform/
│   ├── route/ station/ train/ trainrun/ coach/ seat/
│   └── booking/ fare/ passenger/ audit/
└── tests/
```

Each feature may contain `handler.go`, `service.go`, `repository.go`, `model.go`, `validation.go` and generated-query adapters as needed—not ceremonial layers. **Handlers** translate HTTP/OpenAPI types, call one use case and map errors. **Services** enforce business policy and transaction choreography. **Repositories** expose narrow persistence operations and translate pgx/sqlc results. **Domain models** express entities/value objects and valid transitions without HTTP/database dependencies. **Validation** separates structural input checks from database-backed business checks. **SQL queries** live in `database/queries`, are generated by sqlc and are only called by repository adapters.

Feature responsibilities: route/station own ordered geography; train/coach/seat own rolling-stock inventory; trainrun owns dated service/status; fare owns rule selection/calculation/snapshots; passenger owns normalized/protected details; booking owns idempotent transaction, overlap mapping and lifecycle; audit records append-only events. `app` wires the graph explicitly in `main` using constructors—no DI framework or service locator.

## Runtime design

- Propagate `context.Context` from HTTP through service/repository; never store it on structs. Apply server header/read/write/idle timeouts and a shorter per-request/database statement timeout.
- Configure pgxpool max/min/idle/lifetime from environment and DB capacity; expose pool metrics. Validate connectivity and migration version in `/ready`; `/health` checks only process liveness.
- Use `slog` JSON in production with request/correlation ID, route template, status, duration and safe entity IDs; redact body, contact, token, reference and idempotency values.
- Middleware order: trusted proxy handling → request ID → recoverer → secure headers/CORS → authentication placeholder → rate limit → timeout → route handler → access log/metrics. Panic recovery returns generic 500 and logs stack server-side.
- Allow exact configured CORS origins/methods/headers; no wildcard with credentials. CSRF protection becomes mandatory if cookie authentication is introduced.
- Validate max body size/content type, reject unknown JSON fields and aggregate field errors. Map known domain/SQL errors centrally (`23P01` → 409); do not expose SQL.
- Graceful shutdown: stop accepting, mark unready, allow a configured drain period, cancel background workers, close pool/logger, then exit nonzero if forced. Network calls stay outside database transactions.

Repositories accept a `DBTX` interface so the same generated queries operate on pool or transaction. A transaction runner belongs to `database`; services supply the callback. This preserves atomic booking+audit+idempotency without leaking `pgx.Tx` broadly.

Rate limiting begins in-process per trusted client/IP and stricter per booking-reference action; distributed enforcement may use a gateway/Redis later. Authorization is deny-by-default with owner/support/admin policies when identity is implemented.
